# 分页——数据层负责分页，前端只调用，用"查看更多"

## 核心规范

**原则**：分页标记（offset/cursor/页码）只在数据源层面产生和管理，前端所有展示位都通过调用获取，不做分页状态计算。交互上统一用"查看更多"按钮，不用传统 1/2/3 页码。

## 一、架构角色划分

| 层级 | 职责 | 不做什么 |
|---|---|---|
| **数据源（API/后端）** | 接收分页参数，返回数据 + 分页标记 | 不管前端怎么展示 |
| **前端** | 调用 API 获取分页数据，渲染"查看更多"按钮 | 不自己算总数/页码/偏移量 |

**工作流**：
1. 前端请求第 1 页数据
2. 后端返回：`{ items: [...], next_cursor: "abc123", has_more: true }`
3. 前端渲染数据 + "查看更多"按钮
4. 用户点击，前端带上 `cursor=abc123` 再次请求
5. 重复，直到 `has_more: false`

## 二、"查看更多" vs 传统页码

| 维度 | "查看更多" | 传统页码（1, 2, 3...） |
|---|---|---|
| 实现复杂度 | 低，前端只需一个按钮 | 高，需要页码计算、当前页高亮、跳页 |
| 适用数据量 | 中到大 | 确定可控 |
| 用户体验 | 自然滚动，无中断 | 可跳页，精准定位 |
| URL 同步 | 不需要（每次追加） | 需要（?page=3 可分享） |
| SEO | 差，爬虫只看到首屏 | 好，每页独立 URL 可收录 |
| 对后端的依赖 | cursor-based 分页（性能好） | offset-based 分页（简单但性能差） |
| 数据变更时 | 无影响（cursor 不依赖偏移量） | 可能跳页或重复（offset 偏移） |

## 三、何时该用哪种

| 场景 | 推荐方案 | 原因 |
|---|---|---|
| 新闻列表、动态流、资讯 | "查看更多" | 用户不需要跳页，往下看就行 |
| 搜索结果、商品列表 | "查看更多" | 数据量大且实时变化，页码不可靠 |
| 后台管理列表、报表 | 传统页码 | 需要定位到特定页，操作精确 |
| SEO 重要（博客、文章） | 传统页码 | 每页独立 URL 必须可收录 |
| 移动端 | "查看更多" | 屏幕小，页码点不准 |

## 四、与搜索页刷新策略的关联

本规范与前一篇"搜索/筛选页面刷新策略"（笔记 `1779962304`）互补：

- "查看更多"天然配合**局部刷新**：追加内容，不刷新整页
- 如果项目走**全页刷新**方案，分页用传统页码 + URL 参数（`?page=2`）更自然
- 标准项目默认组合：**全页刷新 + 传统页码 + URL 参数**
- 高预算项目可选：**局部加载 + "查看更多" + cursor 分页**

## 五、实现要点

1. **后端必须用 cursor-based 分页**（非 offset），否则数据变更时"查看更多"会出现重复或遗漏
2. **"查看更多"按钮状态**：正常 → 加载中 → 已全部加载（按钮变灰/消失）→ 加载失败（重试按钮）
3. **不要在前端计算 totalCount 再判断是否显示按钮**——直接用后端返回的 `has_more` 字段
4. **空状态单独处理**：如果第一页就为空，不能显示"查看更多"

## 注意事项

- "查看更多"和"无限滚动"是两回事：前者需要用户主动点击，后者自动触发。对于标准预算项目，用"查看更多"更可控、更省事
- 分页状态不要存前端本地（Vuex/Redux），每次从 API 拿最新数据
- 后端返回的 `next_cursor` 前端只需原样传回，不需要理解内容

## 适用场景

- 标准预算的企业网站、B2B 官网
- 新闻/文章/产品列表页
- 与客户报价时明确这是标准方案，不是"缺功能"
