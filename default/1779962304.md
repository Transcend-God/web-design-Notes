# 搜索/筛选页面的刷新策略——全页刷新 vs 局部刷新

## 核心规范

### 默认方案：全页刷新 + URL 参数（推荐）

筛选/搜索条件变化时，刷新整个页面，URL 带查询参数。

示例：`/search?keyword=steel&category=pipe&page=2`

优点：
- URL 即状态，可直接复制发给客户
- 浏览器前进后退天然可用
- 开发简单，后端主导，前端几乎无状态管理负担
- SEO 友好，搜索引擎可直接收录带参数的页面
- 排查问题方便——客户发个 URL 就能复现

适用：标准预算项目、企业官网、B2B 网站、内容型网站

---

### 进阶方案：局部刷新 + URL 同步（仅高预算客户）

使用 AJAX/fetch 局部刷新结果区域，同时通过 history.pushState 同步 URL。

优点：体验流畅，无页面闪烁

缺点：
- 需处理浏览器前进/后退（监听 popstate 事件还原筛选状态）
- 初次加载时需从 URL 反向解析所有筛选参数初始化界面
- 筛选组件状态与 URL 的双向同步逻辑复杂
- 分页、排序、多条件组合时状态管理容易出 bug
- 开发周期长，测试成本高
- 出问题时客户截个图你看不出他的筛选条件

适用：高预算客户、C 端产品、SPA 单页应用

---

### 方案对比

| 维度 | 全页刷新 | 局部刷新 + URL 同步 |
|---|---|---|
| URL 可分享 | 天然支持 | 需要额外实现 pushState |
| 开发成本 | 低 | 高（2-3 倍工时） |
| 浏览器前进后退 | 自动 | 需手动处理 popstate |
| SEO | 支持 | 需 SSR 配合 |
| 用户体验 | 有闪烁 | 流畅 |
| 出问题排查 | 容易（URL 即现场） | 困难（状态在内存里） |
| 推荐客户群 | 所有客户 | 仅高预算客户 |

---

### 服务器视角的影响

| 维度 | 全页刷新 | 局部刷新 + URL 同步 |
|---|---|---|
| 请求类型 | 每次筛选 = 完整页面请求 | 首次完整页面，后续 = JSON API 请求 |
| 服务器渲染压力 | 高（每次渲染完整 HTML） | 低（只返回 JSON 数据） |
| 带宽消耗 | 大（HTML+CSS+JS 全量） | 小（仅数据载荷） |
| 缓存策略 | 简单，按 URL 做页面缓存即可 | 复杂，需区分页面缓存和 API 缓存 |
| 服务器日志 | 完整请求链路，便于排查 | API 日志和页面日志分离，排查需拼凑 |
| 数据库查询 | 每次请求跑完整查询+渲染 | API 只跑查询，不渲染 HTML |
| 架构复杂度 | 单体应用即可 | 需要前端 SPA + 后端 API 分离，或 SSR+API 混合 |
| 并发承载 | 单次请求重，高并发需更多资源 | 单次请求轻，同样的服务器可承载更高并发 |

**关键结论**：
- 全页刷新对服务器压力更大（每次渲染完整页面），但架构简单、运维成本低。适合流量不大的企业站
- 局部刷新服务器更省资源（只返回 JSON），但需要额外维护一套 API，前后端分离架构
- **对于大多数企业官网和 B2B 网站**：服务器压力根本不是瓶颈（日 PV 几千到几万），全页刷新完全够用。不要为了「省服务器」把架构搞复杂
- **真正需要局部刷新的场景**：日 PV 百万以上、搜索结果实时性要求高、页面其他模块有独立交互需求

---

## 注意事项

- **不要折中**：要么全页刷新，要么正经做 pushState 同步。最差方案是局部刷新但 URL 不变——用户刷新页面就回到初始状态，体验灾难
- **如果是 WordPress 等 CMS 建站**：直接用全页刷新方案，插件生态天然支持 URL 参数筛选
- **报价时要明确**：跟客户说清楚「搜索结果页」有两种实现方式，差价体现在这里。不要让客户以为局部刷新是标配
- **筛选条件多时**：全页刷新方案注意 URL 长度限制（浏览器约 2000 字符），条件过多建议用 POST + 短链或服务端存储

## 适用场景

- 向客户报价/出方案时，搜索页实现方式的选择和说明
- 网页设计评审时，检查搜索页的刷新策略是否与客户预算匹配
- 开发交接时，明确前端是否需要实现 pushState 状态管理
