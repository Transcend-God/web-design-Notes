# 设计评审工作流

## 工作流概览

```
版本选择(完整/简化) -> 项目路径指定 -> 文件发现 -> 图像识别(Kimi) -> 分析(DeepSeek) -> [版本对比？询问主推] -> 输出
```

**模型分工（强制）**：
- 图像识别/读取设计稿 → 调用 Kimi (kimi-k2.6)，通过 `sessions_spawn` 指定 model
- 分析/文案/讲稿输出 → 使用 DeepSeek（当前默认模型）
- 原因：Kimi 多模态识别能力更强，能更准确地描述设计稿中的文字、布局、色彩细节；DeepSeek 的分析和文案能力更强

## 第〇步：输出版本选择（任务开始时必问）

**在进入文件发现之前，必须先询问用户需要哪种输出版本：**

| 版本 | 定位 | 适用场景 | 文档特点 |
|------|------|---------|---------|
| **完整版** | 逐板块深度拆解 | 客户正式陈述、内部详细评审 | 每个板块含内容说明+功能说明+设计交互三维分析，有对比表格，篇幅较长 |
| **简化版** | 概括性总结讲述 | 快速汇报、高层预览 | 按叙事逻辑概括性讲述，不逐板块拆解，只保留核心对比和结论，篇幅精简 |

询问示例：
> "需要输出完整版（逐板块拆解，详细讲稿）还是简化版（概括性总结，快速预览）？"

用户确认后，按选定版本组织后续分析和输出。不指定时默认输出完整版。

原因：不同场景对信息密度需求不同——客户正式提案需要逐板块深度分析，内部快速同步只需要概括性结论。

## 第一步：项目文件发现

1. 用户提供项目根目录路径（含中文路径时优先用 `cmd /c dir` 避免 PowerShell 编码问题）
2. 列出所有子目录和文件，识别：
   - 设计稿件（.jpg/.png/.jpeg/.webp）—— 核心评审对象
   - 辅助文档（.pdf/.docx）—— 品牌手册/需求文档
   - 素材资源（.mp4/.mov）—— 视频素材
   - 照片资源 —— 用于理解图片选用策略
3. 如果有子目录（如 `页面/`、`素材/`），按分类归纳整理
4. 将发现的资源报告给用户确认范围

## 第二步：图像识别（Kimi 子代理）

**在分析之前，必须先将所有设计稿交给 Kimi 做图像识别。**

1. 使用 `sessions_spawn` 创建 Kimi 子会话，model 设为 `kimi-k2.6`
2. 将设计稿文件路径作为 attachments 传入，或在 task 中指定路径让 Kimi 用 read 工具加载
3. Kimi 需要对每张设计稿输出详细的文字描述，包括：
   - 每个内容板块的标题和正文文字（尽可能还原原文）
   - 每个板块的布局结构（左文右图/上图下文/卡片式等）
   - 配色方案（主色、辅色、点缀色的具体色值和用途）
   - 图片/图标的类型和风格
   - 按钮和CTA的位置与文案
   - 导航菜单的结构和文字
4. 如果图片较多（>5张），分批交给 Kimi 处理
5. 收到 Kimi 的文字描述后，再进入分析阶段

## 第三步：逐稿加载（DeepSeek 分析准备）

1. 基于 Kimi 返回的文字描述，按模块分组（如：首页 --> 关于我们 --> 新闻 --> 教育 --> 特色 --> 招生 --> 其他）
2. 对于标注了「弹窗」「交互版」「多个版本」的稿件，单独标记
3. 全部 Kimi 描述收集完毕后进入分析阶段

## 第四步：双维度分析（DeepSeek）

对每一张/每一组设计稿件，从两个维度展开分析。

详细分析框架见 `references/analysis-framework.md`。

### 设计形式维度

- **色彩体系**：主色/辅色/基底的色值、情绪、品牌关联
- **字体排版**：标题字/正文字选择、层级、行距、阅读舒适度
- **布局结构**：网格系统、模块分区、长滚动节奏、视觉呼吸点
- **图形语言**：图标风格、装饰元素、辅助图形
- **图片策略**：实拍vs素材、色调处理、情绪传达

### 交互功能维度

- **导航系统**：信息架构、一级/二级菜单、当前态、吸顶
- **滚动交互**：视差、锚点、滚动触发动画
- **弹窗/模态框**：触发条件、内容展示、关闭方式
- **特色交互**：标注了交互版的页面单独分析
- **动效设计**：hover反馈、页面过渡、数据动画、弹窗进出
- **响应式**：PC端为主还是有多端方案

### 输出格式

输出内容应包含：
1. 项目概要（客户、设计范围、页面数、分辨率）
2. 设计形式分析（色彩/字体/布局/图形/图片）
3. 交互功能分析（每类交互逐一说明）
4. 整体评价（亮点+优化建议）

## 第四步-A：版本对比场景（如有多版本稿件）

### 版本检测机制（按命名去重，不靠序号区分）

**在文件发现阶段，通过以下逻辑自动检测多版本稿件，不依赖固定的序号前缀：**

1. 将所有设计稿文件名去掉扩展名，按以下模式剥离前导标识符：
   - 单字符+连字符：`a-首页` → 剥离 `a-`，保留 `首页`
   - 序号+连字符：`方案A-首页` → 剥离 `方案A-`，保留 `首页`
   - 字母/数字后缀：`首页_v1` → 剥离 `_v1`，保留 `首页`
   - 空格/括号前缀：`(改) 首页` → 剥离 `(改) `，保留 `首页`
2. 剥离后，若多个文件名**核心名称完全相同**，则属于同一页面的不同版本
3. 示例：`a-首页.jpg`、`b-首页.jpg`、`c-首页.jpg` → 三个文件都是「首页」的版本
4. 示例：`方案一-关于我们.png`、`方案二-关于我们.png` → 两个文件都是「关于我们」的版本
5. 示例：`首页.jpg`、`首页_v2.jpg` → 判断为同一页面的两个版本
6. 去重后仅出现一次的文件名 = 单版本页面，无需对比

**检测到多版本后，在执行对比分析之前启动以下流程：**

1. 将检测结果报告给用户（如「检测到『首页』页面有 2 个版本：a-首页 和 b-首页」）
2. 按分组的版本同时分析，先以纯文本输出对比差异
3. **在输出正式讲稿文档之前，明确询问用户：你更倾向哪个版本？以哪个为主推？**
4. 收到用户确认后，再以指定主推版本为结论输出 Word 讲稿文档
5. 如果用户没有明确偏好，可以提供客观判断建议，但仍需用户拍板

原因：设计稿对比的结论（推荐哪个版本）不是纯技术判断，涉及品牌策略、客户偏好等主观因素，AI 不应替用户做这个决策。

## 第五步：输出文档（DeepSeek）

根据第〇步选择的版本和用户要求输出：

### A. 完整版讲稿（逐板块深度拆解）
- 封面 + 目录 + 逐板块详解
- **每板块含三个维度**：内容说明（这个板块讲了什么）、功能说明（在用户浏览中起什么作用）、设计交互（视觉和动效方案）
- 语气：像在给客户做当面汇报，不堆术语，用比喻
- 格式：Word (.docx)，使用 docx-js 生成
- 颜色体系：品牌主色+辅色，呼应设计稿调性
- 如果多版本对比，使用对比表格辅助说明
- 结尾附推荐结论和优化建议

### B. 简化版讲稿（概括性总结讲述）
- 封面 + 按叙事逻辑概括性讲述
- **不逐板块拆解**，而是以叙事线串联：a版用一段文字概括其叙事策略 → b版同样 → 核心差异对比表 → 推荐结论
- 篇幅控制在完整版的30-50%
- 保留核心对比表（板块顺序、独有板块、关键差异）
- 语气同样口语化，但更精炼
- 格式：Word (.docx)

### C. 结构化评审报告（如用户特别要求）
- 表格化对比分析 + 分级打分
- 适合内部设计走查

### D. 纯文本分析（如用户特别要求）
- Markdown 格式
- 适合快速沟通、即时反馈

## 关键规则

1. **先加载后分析**：全部图片加载完毕才开始分析，不边看边评
2. **不凭空发挥**：分析基于设计稿实际内容，不编造不存在的元素
3. **中文路径处理**：除 node/python 执行外，文件操作优先用 `cmd /c` 绕过 PowerShell 编码问题
4. **输出格式由用户决定**：不指定时默认输出口语化讲稿（Word 文档）
5. **并行加载**：图片读取每次 5 张，read 工具支持并行调用
6. **对比必询问**：当存在同页面多版本稿件时，在输出正式文档前必须先询问用户以哪个版本为主推方案，不得在未确认的情况下自行下结论并写入文档
7. **模型分工（强制）**：图像识别必须用 Kimi (kimi-k2.6)，分析和文档输出必须用 DeepSeek。不可用 DeepSeek 直接替代 Kimi 做图像识别
8. **版本选择必问**：任务开始时必须先询问用户需要完整版还是简化版，不得在未确认的情况下直接开始分析
9. **简化版≠敷衍**：简化版是精炼，不是省略。核心对比表格、关键差异、推荐结论一个都不能少
10. **输出语言（强制）**：最终输出文档（Word/Markdown）必须全部使用中文，包括封面、标题、正文、表格、页眉页脚、图表标注等所有内容。设计稿件中的英文内容可在分析描述中保留原文并附加中文备注（如：「Slogan：『智算世界，芯耀东方』（Smart Computing World）」），方便客户直观理解
